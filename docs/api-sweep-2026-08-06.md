# API sweep, 2026-08-06

Every operation in `api/openapi.yaml` — 50 of them — driven against the real
`~/.ssh` through the built binary, with a session obtained the way the browser
obtains one. 207 cases. `~/.ssh` was backed up first and restored afterwards;
the file set, every file's bytes, the directory set and every alias's `ssh -G`
output are identical to how the sweep found them.

Network rule: `aida-serv-1` was the only host contacted. `terminal/launch` was
driven only through its refusals (a success opens a window) and
`remote-keys/register` was not run at all (it writes to a remote
`authorized_keys`).

The harness and the per-phase results are in the session scratchpad
(`harness.py`, `phase0.py` … `phase67.py`, `results-*.json`).

## Findings

All seven are fixed and re-verified against the running binary on the real
`~/.ssh`; each entry says how. The seventh was found while fixing the third.


### 1. A rename takes over an alias another file already declares — high

**Fixed.** `planFileEdit` now refuses a rename onto a name any concrete `Host`
block in the resolved graph already declares — the check `move` has always had.
A catch-all is not counted: it matches every alias and declares none, so
counting it would refuse every rename in a configuration ending `Host *`.
The refusal is `409 alias_already_declared` rather than the generic
`invalid_edit`, because nothing about the request is malformed. Re-verified:
the rename is refused with that code and `ssh -G abciq` still answers `qes02`.


`kind: "rename"` accepts a new alias that another configuration file declares,
writes it, and reports nothing. `kind: "move"` refuses exactly this situation
with `ErrDuplicateDestinationAlias` (`move.go:78`); rename has no equivalent
check.

Observed live. Renaming a host inside a group file to `abciq` — a real host in
the entry file — left two `Host abciq` blocks, and because the generated region
sits above the entry file's own blocks, the group file won:

```
before   ssh -G abciq → hostname qes02          user qch10335hf
after    ssh -G abciq → hostname 192.168.0.145   user tv
```

The save answered `200` with a diff of the file it changed and no notice about
the file it had just taken precedence over.

### 2. A cross-file duplicate alias is invisible where a user would see it — high

**Fixed.** `ProjectHosts` keys the duplicate check on the alias alone, so the
walk's reading order decides the winner and every later block is flagged;
`ComputeEffective` gained the same detection so the host detail's Effective tab
says it too. Re-verified with a controlled duplicate: the overview answers
`duplicate_alias` and flags the shadowed entry, and the host detail carries the
notice.


`projection.go:236` builds the duplicate key from the file's absolute path:

```go
key := entry.File.Absolute + "\x00" + alias
```

so the check only ever fires for two blocks in the *same* file — the case that
needs no help, since a reader sees both at once. The case OpenSSH's
first-one-wins rule is actually about, two files, never fires.

Three surfaces look for this, and one reports it:

| Endpoint | Engine | Reports a cross-file duplicate |
| --- | --- | --- |
| `/api/v1/config/overview` | `application.ProjectHosts` | no — no notice, `duplicate` flag never set |
| `/api/v1/config/host` | `application.ComputeEffective` | no — has no duplicate detection at all |
| `/api/v1/diagnostics/effective` | `internal/effective.Project` | yes, naming the losing block |

Verified with a controlled duplicate: `overview.notices` was `[]`, no host
carried `duplicate`, both host details returned `complexities: null`, and only
the diagnostics endpoint answered `duplicate_alias` at `config:16`.

The connections tree renders a duplicate marker (`ConnectionTree.tsx:204`) that
therefore cannot appear for this case, and the notice text —"Another block
declares the same alias. OpenSSH uses the first one it reads."— describes
precisely the situation that cannot produce it.

This is also the reporting the group region's new placement was traded against;
that reasoning is corrected in `region.go` and in the roadmap.

### 3. Deleting a group parks a connection where nothing reads it, silently — medium

**Fixed.** `group_file_unreached` is now emitted in two places: the group-delete
preview, naming each connection that will stop being read *before* the save,
and the overview, which walks `connections/` and reports every `.conf` file the
Include graph does not reach. Re-verified: the delete preview carries the
notice and so does the overview afterwards.


`grouprename.go:438` moves a connection to `connections/<name>` when a delete
names no destination, with the comment:

> An ungrouped connection file has no home that anything reads, so a delete
> without a destination leaves it directly under `connections/` where the UI
> reports it as unreached.

`NoticeGroupFileUnreached` is declared at `groups.go:21` and **never emitted** —
nothing in Go produces it and the web messages have no string for it.

Observed: after `POST /api/v1/config/groups/delete {"name": ...}` the overview
went from 21 hosts to 20, the connection was absent, the only notice was an
unrelated `orphan_metadata`, and `ssh -G tv-recoding-local` stopped resolving.
The delete's own preview carried `group_directory_leftover` and nothing about
the connection.

For contrast, `file_rename` handles the same situation correctly: renaming a
file out of its group's glob answers with `include_no_longer_matches` and
`include_now_unreached`.

### 4. A key comment cannot contain a space — medium

**Fixed.** The shell-safe pattern is now `ValidateHardwareComment`, applied only
where it is true — the `ssh-keygen` command line shown for a hardware key.
`ValidateComment`, for a key generated in process, refuses what would damage the
file or its line: a newline, a carriage return, a nul. Re-verified: a key with
the comment `work laptop` is created, and the hardware command still refuses it.


`keys/service.go:40`:

```go
// commentPattern accepts only characters that need no shell quoting, because a
// comment is shown inside a copyable ssh-keygen command line.
var commentPattern = regexp.MustCompile(`^[A-Za-z0-9@._+=:,/-]{0,127}$`)
```

The justification holds for `HardwareCommand`, which builds an `ssh-keygen`
command line for the user to run. A software key is generated in process and its
comment goes to `ssh.MarshalPrivateKey`; it reaches no command line. So the
hardware path's constraint is applied to a path it does not describe.

`POST /api/v1/keys` with `comment: "work laptop"` answers `400 invalid_request`
with no detail, so nothing tells the user that the space is the problem.
`ssh-keygen -C "work laptop"` is ordinary.

### 5. `ssh -G` values are returned without the promised home-path substitution — low

**Fixed.** `Inspect` passes the evaluated values through `SanitiseHomePaths`
before they leave the service. Keywords are left alone: a keyword is a fixed
OpenSSH name and can never hold a path. Re-verified: no home path in the values
and `userknownhostsfile` comes back as `~/.ssh/known_hosts …`.


README, SSH 実行の境界:

> 応答に載せる `ssh` の出力は上限つきで、ホームディレクトリのパスを `~` に置換してから返します。利用者のアカウント名を応答本文へ持ち出さないためです。

`platform.SanitiseHomePaths` has exactly two callers, both for stderr:
`diagnostics/service.go:258` and `remotekey.go:126`. The `values` array of
`/api/v1/diagnostics/effective` is raw `ssh -G` output, so:

```json
{"keyword": "userknownhostsfile",
 "values": ["/Users/aida/.ssh/known_hosts /Users/aida/.ssh/known_hosts2"]}
```

The same request's `stderr`, when there is one, is substituted correctly. It is
a localhost-only API, so the exposure is small; the point is that the rule is
stated without qualification and held on two paths out of three.

### 6. Purging a key leaves it in the agent — informational

**Fixed.** `DELETE /api/v1/keys/{keyId}/agent` removes one identity, wired to the
`Remove` the agent seam already had and offered on any key the agent is holding
— matched by fingerprint, the only thing an agent identity and an inventory item
share. No confirmation token: it destroys nothing and the worst case is one more
passphrase prompt. Re-verified end to end: registered, removed, agent empty.


Registering a key with `POST /api/v1/keys/{id}/agent` and then purging it from
the trash leaves the identity loaded in `ssh-agent`. The Keys screen reports
what the agent holds but offers no way to remove an entry. In this run the
60-second lifetime cleared it, so nothing was left behind.

### 7. A group holding a key could not be deleted without a destination — medium

Found while fixing the third, by a test that put a key in the group.

`groupFileMoves` aimed a connection at `connections/<name>` when no destination
was given but aimed a key at the workspace root, so its directory was `"."` —
which `AbsolutePath` refuses, because it is the root itself. The whole delete
then failed with `path is outside the ssh directory`, which names neither the
cause nor anything the user did, and a group holding a key could not be deleted
at all without naming somewhere else to put its files.

**Fixed.** Both roots are treated the same: with no destination a file lands
directly under its own tree, `connections/` or `keys/`. For a connection that
means nothing reads it, which finding 3 now says outright; for a key it means
only its directory changed.

## What was verified as correct

Worth recording, because these are the parts that would be expensive to get
wrong and they hold on real data:

- **The security envelope.** Fetch Metadata refused on every route including
  GET; `Host`, `Origin` and CSRF each refused independently; a request with no
  session cookie got `401`; the bootstrap fragment answered `409 bootstrap_used`
  on replay. The 2 MiB ceiling refused a declared over-length body before the
  handler ran, including on `/api/v1/diagnostics/config`, which reads no body,
  and cut off a chunked one. An unknown `/api/` path returned `404` without
  falling back to the SPA.
- **Action tokens.** Single use, bound to both kind and target: a reveal token
  would not work on another key, a purge token would not work as a reveal, and a
  reachability token issued for `aida-serv-1` was refused for another alias —
  which is what kept the sweep off every other host.
- **`known_hosts`.** 974 entries parsed; a delete carrying a wrong digest was
  refused and one carrying the shown digest succeeded, and after adding and
  removing an entry the 251,322-byte file was byte-identical.
- **Key material.** Reveal answered with `Cache-Control: no-store`; no key
  material appeared anywhere in `history`; a passphrase change left no copy of
  the key under `sshc/backups/`; `sshc/` was excluded from the key scan.
- **The password vault.** The sealed file contained neither the alias nor the
  password. PR #8's eligibility answered correctly against real data —
  `identity_file_configured` as a warning that does not block, and no false
  `host_key_unknown` for a host that is in `known_hosts`.
- **Sync.** Refused a non-loopback plain-http endpoint, refused an unknown
  direction, and never echoed the secret access key back in its status.
- **The three defects fixed earlier today.** `mdx-dataset`, `Dubguild` and
  `qas.q.abci.ai` are read back from their groups through the Include graph, and
  the region stayed above every `Host` line through a group declaration, a host
  move, a group rename and a group delete.

## Cases where the sweep itself was wrong

Recorded so the counts above are honest:

- `host_fields` `set`/`remove` need a `line`; `add` is the action for a new
  directive. Three cases failed on a malformed request.
- The `known_hosts` delete token binds to the file path, not the entry line.
  Three cases failed on a wrongly-targeted token; the delete works.
- `diagnostics/config` has no `dangerousDirectives` field — that reporting lives
  on `diagnostics/effective` and `remote-keys/plan`, both of which carry the
  real `ProxyCommand` with its token warning.
- `terminal/command` answering `200` for an unsafe alias with
  `launchable: false` and a warning is the documented behaviour, not a defect.
- A `move` whose `base` does not contain the alias answers `404`, not a
  conflict. With a realistic stale base — the alias present, the file changed
  underneath — it answers `409` with a conflict report, which is the case the
  precondition is for.
