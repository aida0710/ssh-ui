# sshc Delivery Roadmap

The approved design spans six independently reviewable subsystems. Each subsystem receives its own implementation plan before its code is changed, and each leaves the repository in a runnable, testable state.

1. **Foundation** — secure localhost process, OpenAPI contract, embedded React shell, macOS browser launch.
2. **Lossless config engine** — byte-preserving parser, Include graph, safe filesystem transactions, journals and history.
3. **Connections UI and groups** — form/Raw synchronization, Include explorer, group inheritance, metadata and diffs.
4. **Key vault** — inventory, generation, passphrase handling, reveal, agent/Keychain integration, trash and restore.
5. **SSH integrations** — effective config, ProxyJump diagnostics, Terminal launch, Known Hosts and remote public-key registration.
6. **Hardening and release** — fuzzing, race tests, E2E, CSP and injection suite, single-binary packaging and acceptance checks.

Plans are executed in this order. A later plan may consume only interfaces committed by earlier plans. No plan may run against the user's real `~/.ssh` in automated tests.

- Follow-up `sshc-directory-groups`: **delivered on `main`**; plan `2026-08-05-sshc-directory-groups-implementation-plan.md`. A group is now a real directory: `connections/<group>/*.conf` and `keys/<group>/`, declared by one generated `Include` line per group inside two marker comments in `~/.ssh/config`, deepest group first and `groups.sshc.conf` last. `metadata.json` is schema 2 and carries no `group` and no `parent` — membership is the directory, the hierarchy is the name, and metadata keeps only presentation. Moving a host into a group, moving or renaming a key, and renaming or removing a group are each one journalled transaction containing the file moves, every rewritten `IdentityFile`/`CertificateFile`, the region, the compiled settings file and the metadata identities. Backwards compatibility was dropped at the user's explicit instruction, so the opt-in migration the plan describes (Task 10) was **not** built: an existing workspace keeps its current layout, its hosts are ungrouped, and the user moves them one at a time through the move control. The two names `connections` and `keys` are fixed, not configurable (plan open question 4, still unanswered — see below).

  Of the plan's three risks, one is closed and two are bounded rather than closed. The overlay gap was already fixed on `main` before this work. A relocation is refused while an unresolved `IdentityFile`/`CertificateFile` could name the moved file, using the reason-narrowed rule (a definite path outside the workspace cannot be it; a relative path is compared by base name; an unimplemented expansion always blocks) rather than the plan's stricter Decision 5 rule, because Decision 5 chose strictness on the strength of a migration that now does not exist. Nothing indexes a file behind an unsupported `Include` expansion, and nothing outside the Include graph — `ssh -i`, `ssh -F`, `core.sshCommand`, a LaunchAgent, `/etc/ssh/ssh_config` — can be seen at all; the preview says so and the suite cannot prove it. The region position is still decided by `pattern == "*"` or the first `Match`, but a concrete `Host` block after that position now refuses the insertion outright rather than changing precedence silently.

  One defect in previously merged code was found and closed by this work: `keys.Rename`, shipped in the previous change, committed its configuration rewrites through the key vault's own `storage.Manager`, which deliberately has no configuration validator. Configuration bytes were reaching disk without the re-parse and re-resolve every other write gets. Key relocation now lives in `internal/application` and commits through the configuration manager; the key files travel as `storage.Move`, which the validator never parses, so both halves get the treatment they need. The route moved from `POST /api/v1/keys/{keyId}/name` to `POST /api/v1/keys/{keyId}/location`, which takes an optional name and an optional group and therefore serves a rename, a move and both at once.
- Follow-up `sshc-password-authentication`: **delivered**; plan `2026-08-05-sshc-password-authentication-implementation-plan.md`. Stores the remote account's password and hands it to `ssh` through `SSH_ASKPASS` with `SSH_ASKPASS_REQUIRE=force`, verified against the installed client before the plan was written — no `sshpass`, no `expect`, no new module.

  **The plan's storage decision was reversed during implementation.** It said the macOS login Keychain; the user asked for passwords to sync, and a Keychain item belongs to a machine. The store is now `~/.ssh/sshc/secrets`, AES-256-GCM with an Argon2id key from a passphrase this application never stores, so it travels with the workspace. Neither the passwords nor the aliases appear in the sealed bytes. That also removed the plan's unclosable risk: the Keychain design's confused deputy — anything that could execute the helper could ask it for any password, forever — is gone, because the helper holds no key. It asks the running, unlocked sshc over loopback with a single-use token bound to one alias, refuses any endpoint that is not 127.0.0.1, and answers one prompt shape. `/askpass` is outside `/api/` and authenticates by token alone.

  Reading a sealed envelope needs a cost ceiling, found by this package's own tamper test: one flipped bit in the KDF cost field asked for about ninety minutes of one core, and the test hung for five minutes. The file arrives from other machines, so a hostile header is input and an unlock that never returns is a denial of service. `internal/envelope` bounds time, memory and threads before deriving anything; the header is authenticated, so this is not a weakening.

  **Not built:** the plan's four eligibility blockers (an `IdentityFile` is configured, the host key is unknown, `PasswordAuthentication no`, a non-simple alias). The panel offers to store a password for any host and states the host-key precondition in prose instead of enforcing it.
- Follow-up `sshc-remote-sync`: **delivered**; plan `2026-08-05-sshc-remote-sync-implementation-plan.md`. The whole workspace — entry file, every included file inside `~/.ssh`, `metadata.json`, the password vault and the private keys — travels as one AES-256-GCM snapshot over a stdlib SigV4 signer. One object rather than one per file, because a configuration is only meaningful as a set. A push is a compare-and-swap on the object's ETag; a pull is one `storage.Request`, so it inherits the validator, the generational backups, the journal and the existing preview, and private keys carry `SkipBackup`.

  **The plan's two open assertions are now one.** Conditional `PUT` is verified: `internal/objectstore` and `internal/remotesync` have integration suites that run against a real S3 implementation, and SeaweedFS honours both `If-None-Match: *` and `If-Match`, refusing a stale write with 412. **R2 itself is still unverified** — nobody has run these against a real Cloudflare bucket, and the only thing established is that the client is correct against a server that did not read this repository. The second assertion stands: `golang.org/x/crypto/argon2` links `golang.org/x/sys` into the shipped binary for the first time, which the release check should be told. `go.mod` and `go.sum` are unchanged.

  **Sync direction is now chosen per machine.** `both` (the default), `push` — this machine never has another machine's bytes applied to it — or `pull`, which never writes to the bucket. It governs the two writes and nothing else: a preview reads the bucket and writes nothing, so a send-only machine can still be told how far behind it is. It travels with the other bucket settings, which are supplied per run and never written into the workspace.

  **Not built:** automatic push. Pushing is a deliberate act; the plan's post-commit debounced queue does not exist.
- Follow-up `sshc-file-operations`: **delivered**, with one part of its original scope still open. Journalled directory create and remove exist (`storage.DirectoryCreate`, `storage.DirectoryRemoval`, rolled back by recreating or removing an empty directory), and the Config Explorer can now rename and delete a configuration file. Both carry the `Include` lines that named the file: a rename rewrites every literal one, a delete removes them, a glob is left alone, and the preview reports a rename that takes the file out of a glob's reach or lands it where no `Include` reaches. An `Include` this application will not rewrite — an absolute path or a tilde — is reported and left untouched. The entry file is refused.

  A configuration delete keeps a generational backup, so History offers the file back like every other change. `storage.Removal` gained an opt-in `Backup` for it; the permanent key purge keeps the irreversibility it was given deliberately, and a test asserts that a purge still copies nothing into the backup directory.

  **Still open:** directory *rename* as a journalled action. A group rename is still N file moves, so it still leaves its emptied source directory behind, reported as `group_directory_leftover` and never removed.

- Integration test infrastructure: `make integration-up` starts SeaweedFS and an sshd in containers, `make integration` runs the suites that need them, `make integration-down` removes them. CI runs the same. Both suites **skip** when their environment variables are unset, so `make test` stays hermetic and offline. They exist for the two questions a fake cannot answer: what a real object store does with a conditional `PUT`, and whether OpenSSH accepts what the askpass helper hands it. The second is the automatable core of manual check M1; M1 itself remains 未実施 because it is about a host the user controls, not a container.

  `internal/objectstore` now permits plain http to a loopback host. Anything else must still be https. A loopback connection cannot be observed off the machine, and the alternative was having no integration coverage at all.

- **`connections` and `keys` are still fixed names.** Requested and not built. They are compile-time constants in three packages — `application.ConnectionsDirectory`, `application.KeysDirectory`, `keys.KeysDirectoryName` — and the sync layer marks a snapshot entry secret by the literal prefix `keys/`. Making them configurable is not a rename: it is threading a layout through every path decision in the workspace, including the reserved-name policy that currently refuses a group called `keys`, and deciding what happens to an existing workspace when the setting changes. The cheapest sound shape is to put a `Layout{Connections, Keys}` on `storage.Workspace`, which is already the one object all three packages hold, turn `GroupDirectory`/`GroupKeyDirectory`/`GroupOfPath`/`GroupOfKeyPath` into methods on it, and read it from `metadata.json`. That is a path-handling change across the whole workspace boundary and it was not worth doing at the end of a long session; it is written down here so the next one starts from the design rather than from the question.

## Three defects that made a group declaration do nothing

Found by reading the author's own `~/.ssh` rather than a fixture, and each one on its own enough to make a connection moved into a group invisible to OpenSSH. All three are closed. They are recorded together because they share a cause: every automated fixture was tidier than a real entry file, and the one shape that mattered — a `config` full of concrete `Host` blocks and no catch-all — was never exercised at any layer.

- **The destination name could not match the Include that was supposed to read it.** `resolveDestination` kept the source file's base name, which is correct for `conf.d/10-home.conf` and wrong for the entry file: a move out of `config` wrote `connections/<group>/config`, and the group's own pattern is `connections/<group>/*.conf`. Since the entry file is where every ungrouped connection starts, this was the commonest move in the application. The name now passes through `GroupFileName`. The preview did carry `destination_not_included`, but it also fired on every correct first move into a group — a new file is not in the Include graph yet — so it was noise exactly where it needed to be signal. It now consults the declared group patterns and stays quiet when one of them will read the file.
- **Moving a connection carried the group declarations away with it.** A block's range runs to the next header, and the region is inserted just before the first catch-all, so in every entry file that declares a group the region sits *inside* the range of the concrete block above it. `ExtractHostBlock` took the whole range, so moving that one connection emptied the region out of the entry file and appended the Include lines to a group file. The entry file was left holding a single end marker, which `FindRegion` then refuses as damaged. `ProjectHostForm` built `Raw` over the same range, so the Raw editor showed the region as part of the connection and would have written it back. Both now clamp with `ClampToRegion`.
- **The region was written where OpenSSH would not act on it.** `regionPosition` inserted before the first catch-all, or at the end of the file when there was none — and the end of a file that declares any `Host` block is inside the last one. An `Include` belongs to the block it is written under, and OpenSSH applies an included file's options only when that block matches, so both positions declared the groups to one unrelated host and to nothing else. Verified against OpenSSH 10.2p1 before the fix was written: a top-level `Include` applies, the same line below a `Host` line does not, and a blank line between them changes nothing. The region now goes above the first `Host`/`Match` line, and an existing region found inside a block is moved rather than replaced in place.

  `checkExistingIncludes` had documented this rule correctly — "One written inside a Host or Match block is conditional: it is read when connecting to that host and at no other time" — and the region planner it sits next to broke it. Knowing a rule and encoding it in one function does not make the neighbouring function obey it.

  The old placement existed to keep the user's own blocks winning, and that goal is unreachable: there is no position that is both below a `Host` block and unconditional. So the group files are now read first, and an alias written in both places resolves to the group file. `ErrRegionPositionAmbiguous` refused a save on the strength of position alone; it is deleted, on the reasoning that the resolved graph reports `duplicate_alias` precisely where the refusal only guessed.

  **That reasoning was checked afterwards against the running application and is only a third true.** `/api/v1/diagnostics/effective` reports a cross-file duplicate and names the losing block. The connections overview and the host detail both report nothing: `ProjectHosts` keys its duplicate check on the file's absolute path, so it fires only for two blocks in one file, and the host detail's Effective tab is built by `application.ComputeEffective`, which has no duplicate detection at all. Deleting the refusal was still right — it refused on position, which is not evidence — but the reporting it was traded for has to be built before the trade is honest. See the API sweep findings below.

## What the API sweep found, and what it cost

Every operation in the contract driven against the author's real `~/.ssh`, 207 cases, recorded in `docs/api-sweep-2026-08-06.md`. Seven defects, all closed. They are worth reading together because six of the seven are the same shape: **a file, an alias or a warning that exists and that nothing reads.**

- **A rename took over an alias another file declared.** `move` had refused this since it was written; `rename` had no such check, answered `200`, and silently moved a live alias to a different machine. Now refused as `409 alias_already_declared`.
- **A cross-file duplicate alias was invisible on the two screens a user looks at.** `ProjectHosts` keyed its check on the file's absolute path, so it fired only for two blocks in one file — the case a reader can already see. The host detail's Effective tab had no detection at all, because it is a second engine (`application.ComputeEffective`) from the one the Diagnostics tab uses (`internal/effective.Project`). Both now report it.
- **`group_file_unreached` was declared and never emitted.** The group delete parks a connection where no Include reaches it, deliberately, on the stated understanding that the interface reports it. Nothing did. It is now emitted by the delete preview *before* the save and by the overview afterwards. `BuildGroupsView` and its other three notice codes are still unwired — see below.
- **A group holding a key could not be deleted without a destination.** The key was aimed at the workspace root, whose directory is `"."`, which `AbsolutePath` refuses; the delete failed with `path is outside the ssh directory`. Found by writing the test for the defect above.
- **A key comment could not contain a space.** The hardware path's shell-quoting rule was applied to in-process generation, where the comment reaches no command line.
- **`ssh -G` values kept the home directory.** `SanitiseHomePaths` had two callers, both for stderr; the values are the same ssh output in the same response.
- **A key could be given to the agent and not taken back.** `DELETE /api/v1/keys/{keyId}/agent` now exists; the `Remove` it needed was already on the seam.

Two things generalise from this.

**A constant that is declared but never referenced is not a feature.** Four notice codes, `BuildGroupsView` and `GroupView` are all defined, tested in isolation, and reachable from nothing. Their tests pass. The README describes `group_not_declared` as behaviour. `go vet` says nothing, because an exported identifier is exported. The only thing that found this was asking the running application for the notice and not getting it.

**Two engines answering one question will diverge.** `application.ComputeEffective` and `internal/effective.Project` both explain what an alias receives; one detected duplicate aliases and one did not, and which screen you were on decided whether you were told. They were not reconciled here — that is a subsystem-sized change — but the divergence is now recorded rather than latent.

**Still unwired:** `BuildGroupsView`, `GroupView`, `NoticeGroupNotDeclared`, `NoticeGroupDirectoryMissing` and `NoticeGroupEmpty`. Wiring them means a `groups` field on the overview, which is a contract change and a screen, so it is a plan rather than a fix. The README claims `group_not_declared` is reported; until that plan runs, it is not.

## Known open defects in merged code

Found while planning subsystem 6, confirmed against the tree, and owned by that plan. They are recorded here so they cannot be lost between plans.

- ~~**Fetch Metadata is checked only on state-changing requests.**~~ Closed by subsystem 6 Task 1. Every `/api/` request is now verified by exact match, and the existing GET tests were repaired by making the request realistic rather than by weakening the middleware. Original report: `internal/httpserver/security.go` verifies `Origin` and `Sec-Fetch-Site` only when the method is not GET or HEAD, so an authenticated API GET skips both. Design §8.1 requires `Host`, `Origin` and Fetch Metadata to be verified without qualification. The `SameSite=Strict` session cookie is what actually stops a cross-site read today, which means one mechanism is carrying a guarantee the design assigns to three. Subsystem 6 Task 1 closes it and repairs the existing tests that will start returning 403.
- ~~**No request body ceiling.**~~ Closed by subsystem 6 Task 2, and closed wider than planned: the ceiling refuses on `Content-Length` before the handler runs, because sweeping every route found two — `/api/v1/diagnostics/config` and `/api/v1/keys/{keyId}/trash` — that read no body at all and therefore accepted an oversized one. `MaxBytesReader` still bounds a chunked request. Original report: Nothing bounds a request body before a handler decodes it, though design §8.1 requires limits on both request bodies and command output. Command output is already bounded by `platform.MaxCapturedOutput`.
- ~~**`make fuzz` runs one target.**~~ Closed by subsystem 6 Task 5. `make fuzz` loops over `FUZZ_TARGETS` and `TestMakefileFuzzTargetsCoverEveryFuzzFunction` fails when a `Fuzz` function is not in the list. Original report: `go test -fuzz` accepts a single target per invocation, so the current recipe silently covers only the parser round trip no matter how many fuzz functions exist.
- ~~**`keys.ValidateFileName` permits reserved names.**~~ Fixed on `main`: reserved names are refused case-insensitively, because a macOS filesystem treats `Config` and `config` as one file. Original report: Generating a key named `config` into an empty `~/.ssh` would create the entry configuration file and fill it with a private key. An existing file is protected by the transaction precondition, so this only bites on a fresh workspace, but the name policy should refuse the names the application itself depends on. Found and reported rather than silently patched by the key vault subsystem, since filename policy is not its to decide.
- ~~**No test reads the log stream.**~~ Closed by subsystem 6 Task 3, with a stated limit — see "Limits of the hardening suite" below. Original report: Several plans state that secrets must never be logged, and none assert it.
- ~~**Two delivered APIs have no interface.**~~ Closed on `main`; both confirmations are now user-facing. Original report: Subsystem 5 reported both rather than inventing a design. `POST /api/v1/known-hosts/add` is covered at the service and endpoint level, but the Known Hosts panel scans and lists unverified candidates without an add affordance, so adding a scanned key is API-only — and design §6.4 requires the confirmation step to be a user-facing one. `POST /api/v1/remote-keys/plan` and `/register` have no panel at all, though design §6.6 describes a user-facing confirmation showing the alias, effective user, fingerprint and intended change.
- ~~**A third delivered API had no interface, and two panels still described delivered work as pending.**~~ Closed on `main`, found by enumerating the shipped features against the route table rather than against a plan. Three defects of one shape: what a screen says it can do had drifted from what the server does.
  - `POST /api/v1/keys/{keyId}/agent` was implemented, tested and unreachable. `web/src/keys/api.ts` even parsed `agentAvailable`, `agentIdentities` and `agentDelegations` and rendered none of them, while the change-passphrase form told the user to "use agent registration" for a control that did not exist. The Keys screen now offers registration per private key with a lifetime and the login Keychain option, and reports what the agent holds and which entries delegate to it. Design §6.3's remaining agent item is closed.
  - The Host editor's `Diagnostics` tab still read "arrive with a later subsystem" after subsystem 5 shipped them. It now runs the real checks, addressed by the open connection: `DiagnosticsPanel` takes an optional fixed host, which also hides the alias field and skips the configuration read. Per the roadmap's own integration note, the tab hands over to subsystem 5's gates rather than inventing a third confirmation.
  - The `Effective` tab claimed the authoritative check was still to come. It now says why the projection is not `ssh -G` — OpenSSH settles some values only once it knows the destination, and only it evaluates `Match` — and offers a button that opens the Diagnostics tab.

  Automated coverage stops where it must. The end-to-end binary is started with `HOME` and `PATH` only, so it can reach no agent, and the spec asserts the refusal rather than a registration. That a real registration works is manual test M3, which now names the control.

- ~~**Six more gaps between what a screen showed and what the server had already computed.**~~ Closed on `main`, found by enumerating the shipped features against the design's §6 and against the fields each response actually carries. The first is a defect; the rest are work the schema described and no screen did.
  - **A failed `ssh -G` rendered nothing at all.** It answers 200 with the reason inside `failure`, so nothing threw, the sources table was empty and every other block was conditional: pressing Explain looked like a no-op. The panel now shows the exit code, the standard error, and whether that output hit `MaxCapturedOutput`.
  - **The engine's own hedges were computed and dropped.** `complexities` is where the projection says it will not answer for a rule — the "complex external rule" the README promises — and it was rendered nowhere, so an unreliable value looked exactly like a reliable one. `route` was likewise dropped, taking design §6.1's connection-route visualisation with it, and `sources` was filtered to the winner, which is the one row that cannot answer "why this and not that". All three are now rendered, with an unresolved hop marked rather than omitted.
  - **The Keys screen dropped `unreadable`, `unresolvedReferences` and `certificate`.** A file the scanner refused to classify was simply absent, so an incomplete inventory looked complete; an expired certificate was indistinguishable from a working one.
  - **Nothing could be copied.** Design §6.1 and §6.3 ask for the command, the public key and the private key to be copyable, and every one of them was text in a `<pre>`. There is now one copy control, which reports a refused clipboard write rather than claiming success.
  - **`colour`, `order` and `orphan` were storable and not editable.** The first two now have controls and sort the tree; `orphan` has a panel that re-associates a stranded note or discards it, and refuses to merge into a host that already has settings rather than deciding which set wins. Before it, the notice told the user to re-associate deliberately and gave them nothing to do it with.
  - **A favourite could be set and not seen.** The star, the colour and the duplicate marker existed only in the `sr-only` description, so a sighted user could set a favourite and then not find it. They are now visible and `aria-hidden`, since the description still carries them.

- ~~**Making a comment mean something mis-attributed it in four places.**~~ Closed on `main` in the change that introduced it, found by reviewing that change rather than by a report. Attaching a comment to the block below it turned a previously inert stray comment into a claim about a specific connection, and four paths moved blocks without moving the claim. Deleting a connection left its description behind, where it became the description of whichever block followed. Moving one did the same, and `ExtractHostBlock` simultaneously stole the *next* block's comment, because a block's range runs to the next header and its tail therefore holds that comment. `ProjectHostForm` built `Raw` over the same range, so the Raw editor and the delete path both wrote back text that included a neighbour's description. Duplicating a connection produced an unexplained copy beside an explained original. All four now end at `File.CommentRun(block.End)` and start at `File.CommentRun(block.Header)`. The lesson is the general one: giving meaning to text that was previously ignored makes every existing path that moves that text a candidate defect, and the paths do not announce themselves.

- ~~**`PlanGroupInclude` counted a conditional Include as a top-level one.**~~ Closed by `sshc-directory-groups`, which deleted the function. It scanned every line of the entry file and returned "already present" for an `Include groups.sshc.conf` written *inside* a `Host` block, without consulting the governing block. The generated settings file was then read only when connecting to that one host, and no top-level Include was ever inserted. `checkExistingIncludes` now skips any Include whose block has a condition.
- ~~**`overlayLoader` modelled neither a move nor a removal.**~~ Closed on `main` ahead of the directory-groups work, because it was wrong regardless. A transaction containing a `storage.Move` was validated and previewed against a world where the file was in two places at once. It now carries a `gone` set alongside `pending`, with a pending write winning over a removal so a move onto an existing path still reads its new contents.
- ~~**Key rename bypassed the configuration validator.**~~ Closed by `sshc-directory-groups`. See the status line above.
- ~~**`effective.Project` walked file order, not load order.**~~ Closed by `sshc-directory-groups`, found by putting the generated region in front of the projection and getting the wrong answer. It iterated `graph.Order` file by file, so every block of `~/.ssh/config` was attributed before any block of an included file. OpenSSH reads an `Include` where the line sits, so a `Host *` written *below* an Include is read *after* the whole included file and loses to it. The projection reported the opposite for every configuration whose defaults sit under its Includes — which is the usual shape, and precisely the shape the group region creates. `TestProjectAttributesTheFirstValueOfEachKeyword` had encoded the wrong answer since it was written. The walk now descends into each Include at its own line, and `TestAnIncludeAboveABlockIsReadBeforeIt` is the smallest fixture that tells the two apart.

## Limits of the hardening suite

Found while executing subsystem 6 and recorded so a later reader does not mistake a green suite for a stronger claim than it makes. None is a defect in shipped behaviour; each bounds what the tests prove.

- **The log scrape sees only the injected logger.** `TestNoLogLineCarriesASecret` reads the `slog.Logger` handed to `app.Build`. A package that reached for the global `slog` default would write somewhere the scrape never looks, and the mutation that proved this was the difference between `slog.Info` (not caught) and `c.Logger().Info` (caught). The scrape also passes trivially today because almost nothing logs, which is why `TestTheLogScrapeWouldNoticeASecret` exists as its control. Any new logging must go through the injected logger.
- **Alias defences are three layers deep, symlink defences two.** A hostile alias is rejected by the HTTP handler, by `diagnostics.Service`, and again where the command is built; a symlinked write is rejected by `Workspace.ResolveForWrite` and by `OSFileSystem.ReadFile`'s `O_NOFOLLOW`. Defence in depth is intended, but it means a route-level test stays green when any single layer is removed. `TestTheProcessSeamRefusesAHostileAliasWithoutTheHTTPGuard` and `TestTheWorkspaceGuardRefusesTraversalAndSymlinksWithoutTheHTTPLayer` exist so each layer is answerable alone; a future guard added to these paths needs the same treatment.
- **Partial failure is injected, not observed.** The journal and transaction tests simulate a failed staging write or rename. Nothing kills the process between the staging write and the rename, so crash recovery is proven by inference from those tests rather than by observation.
- **The committed `internal/ui/dist` bundle can go stale.** It is a build artefact under version control, and the copy on `main` predated the Known Hosts and Remote Keys panels, so a binary built from it would have embedded a UI without them. `make e2e` rebuilds before running and would now fail, but `make build` alone will happily embed whatever is committed. Rebuild the bundle in any change that touches `web/src`.

- **Every fixture gave each `Host` block a concrete alias.** A wildcard-only block such as the `Host *` catch-all that almost every real configuration ends with was therefore never exercised at any layer — Go, Vitest or Playwright — and the connections tree shipped rendering it as a button whose click the page silently swallowed. Fixed on `main` by routing a pattern-rule row to the file view at its line. The defect is unremarkable; the blind spot is not. It was found by running the shipped binary against a throwaway home, which no automated test does, and the same shape of gap can hide anywhere a fixture is more regular than a real file. The stale-bundle hazard above bit twice for the same reason: nothing exercised the artefact a user would actually run.

- **Every fixture was short enough to fit on screen.** No test at any layer rendered a panel taller than the viewport, so nothing noticed that the shell scrolled as a single document: the header and the primary navigation sat in normal flow above a `min-h-screen` body, and reaching the bottom of a real `~/.ssh` carried the session status line and the section buttons off screen. Fixed on `main` by giving the shell one viewport of height and making the navigation and `main` its own scrolling regions. The second half of that fix is the part worth remembering. Clamping the regions was not enough, because the connection tree's `sr-only` descriptions are `position: absolute`, and an absolutely positioned element is clipped by an ancestor's overflow only when that ancestor is its containing block. A statically positioned `main` is not, so those spans resolved against the initial containing block, kept their static offsets far below the fold, and re-extended the document's scrolling area while the panel itself looked correctly clipped. `web/e2e/shell.spec.ts` covers it, and each of its assertions is guarded by one that fails when the fixture is not tall enough to scroll — without that guard both specs pass on the unfixed shell, since nothing scrolls at all.

## Interface limits accepted while closing those gaps

Reported by the agent that built the panels rather than papered over. None is a defect in what was built; each is a consequence of the API shape underneath.

- **An unsupported remote is discovered by connecting to it.** `RemoteKeyPlan.supported` is always true from the server; the probe that learns otherwise lives inside `register`, which answers `422 unsupported_remote`. Design §6.6 reads as though the manual-instructions path could be chosen before any connection, but nothing can know a remote lacks a POSIX shell without asking it. So a user on an unsupported remote opens one connection before being told to proceed by hand. Both paths are implemented and tested; the ordering is inherent, not an oversight.
- ~~**A public key cannot be picked from the inventory.**~~ Closed on `main` by `GET /api/v1/keys/{keyId}/public`, which returns the text of a public key or a certificate and refuses anything else. The Remote Keys panel now picks one from the inventory, filling the path and the key line together. Original report: No endpoint returns a public key's text — `KeyItem` carries `relativePath` and `fingerprint` only — while `RemoteKeyPlanRequest` needs `publicKey`. The user pastes the key line and types the file path instead of selecting from the Keys screen. A read endpoint for a public key's contents would turn that into a selector; a public key is not a secret, so this is a convenience gap rather than a security one.
- **`RemoteKeyPlan.valuesFrom` is a free-form string.** The panel renders the values it knows and falls back to printing the raw string, so an unfamiliar value degrades to jargon rather than to a confident but wrong sentence.

## Integration notes for plans 3, 4 and 5

Plans 3, 4 and 5 were written concurrently against the tree as it stood after subsystem 2. They do not conflict in design, but each was authored without seeing the others' edits, so whoever executes them must expect drift in the shared wiring and reconcile it rather than pasting a plan's wiring step verbatim.

- Execution order stays 3, then 4, then 5. A later plan may consume interfaces the earlier one committed.
- All three add routes to `api/openapi.yaml`, handlers under `internal/httpserver`, and construction code in `internal/app/run.go` and `cmd/sshc/main.go`. Each plan's wiring step describes the shape it expects; adapt it to what is actually in the tree at that point.
- Home directory resolution: plans 3 and 5 agree that `os.UserHomeDir` may be called only from `cmd/sshc`, and plan 5 makes `app.Run` fail with `ErrMissingHome` instead of degrading silently. This supersedes the subsystem 2 acceptance-gate grep, which assumed no package needed a home directory yet.
- Storage primitives: plan 4 Task 4 adds `Move`, `Removal` and `Note` to `storage.Manager`, plus `PendingEntry.Action`/`Target` and `Pending.CanRollback`. Plan 3 is cross-referenced to them and the `sshc-file-operations` follow-up must build on them.
- Dependencies: plan 4 introduces `golang.org/x/crypto v0.54.0` and `golang.org/x/sys v0.47.0`, verified against those exact versions. Plans 3 and 5 add nothing. Read plan 5's "no new dependency" gate as "nothing beyond what plan 4 already committed", not as an unchanged `go.mod` since subsystem 2.
- **Process seam ownership, decided at execution time.** Plans 4 and 5 independently specify `internal/platform/command.go` and `internal/platform/macos/command.go` with incompatible shapes: plan 4 Task 3 defines `Command{Name, Args, Input}`, `CommandResult`, `CommandExecutor`, `macos.NewExecutor`; plan 5 Task 1 defines `Command{Path, Arguments, Stdin, Timeout, StopAfter}`, `Output`, `OutputRunner`, `macos.NewOutputRunner`, `macos.Toolchain` and the alias, hostname and port validators. Plan 5's shape is the superset, so **plan 5 Task 1 is executed first as a shared foundation**, extended so `Toolchain` also resolves `ssh-keygen` and `ssh-add` for the key vault. Plan 4 Tasks 3, 6 and 8 then *consume* `platform.Command`, `platform.Output` and `platform.OutputRunner` instead of creating them, and must not create either command file. This is a deliberate deviation from both documents, recorded here rather than resolved silently at merge time.
- **Action token ownership, decided at execution time.** Plans 4 and 5 both add one-time action tokens to `internal/session/manager.go` with incompatible shapes: plan 4 Task 7 defines `Action{Purpose, Subject}`, `ActionLifetime`, `NewManagerWithClock` and `ErrActionUnknown`/`ErrActionExpired`/`ErrActionMismatch`; plan 5 Task 5 defines `ActionRequest{Kind, Target, Evidence}`, `ActionTokenTTL`, `MaxActionTokensPerSession`, a `Manager.Now` clock field, kind constants and `ErrInvalidAction`/`ErrActionExpired`/`ErrUnknownSession`/`ErrTooManyActions`. Plan 5's is the superset — it binds a token to a digest of the exact evidence shown to the user and caps outstanding tokens — so **the session half of plan 5 Task 5 is executed first as a shared foundation**, with plan 4's two kinds added to the same constant set. Plan 4 Task 7 then keeps only its OpenAPI work and consumes the committed token API; it must not touch `internal/session`.
- **Everything that touches `api/openapi.yaml`, `internal/httpserver`, `internal/session`, `internal/app` or `cmd/sshc` runs serially, one subsystem at a time.** Three plans modify all five. Parallel execution there produces guaranteed conflicts and, worse, silently divergent route tables and generated models.
- Execution tracks after that shared task: plan 3 touches `internal/application`, `internal/httpserver`, `api` and `web`; plan 4 touches `internal/keys`, `internal/storage`, `internal/platform/macos/keyagent*`; plan 5 touches `internal/effective`, `internal/platform` and its own handlers. Only the HTTP, `app.Run` and `main.go` surfaces are shared, so the API and wiring tasks of the three plans run serially at the end, never concurrently.
- Confirmation gates: plan 5 splits design §8.3 into evaluation confirmation (`Match exec` only, since that is the sole directive OpenSSH runs while parsing) and connection confirmation (any executable directive). Plan 3's Host detail `Effective` and `Diagnostics` placeholders must hand over to those gates rather than inventing a third one.

## Toolchain decision

The local machine uses the Go 1.26.5 toolchain through Go's official toolchain switching, alongside Node 22.19.0, npm 11.7.0 and OpenSSH 10.2p1. The foundation therefore targets Echo v5.3.1 directly. Go, npm and project dependency installation were explicitly approved on 2026-08-04.

Frontend versions selected for the foundation are React 19.2.8, Vite 8.1.5, Tailwind CSS 4.3.3, TypeScript 5.9.3 and Vitest 4.1.1. TypeScript stays on the latest 5.x release because openapi-typescript 7.13.0 declares a `^5.x` peer dependency. Package-lock and go.sum are committed so all transitive versions remain reproducible.
